# joget-analyzer-web

Joget DX のアプリケーションパッケージ（`.jwa`）とプラグインソースを**リバース解析**するツールです。プロジェクトディレクトリを指定すると、設計書・影響分析・呼び出し関係図・RAG チャンクを自動生成します。

UI は**日本語**です。

> 事実は解析で · 意味づけは AI で —— 構造的な結論はすべてローカル解析によるもので、外部サービスもデータベースも使いません。

---

## 入力方法

**ローカルプロジェクトのディレクトリを指定**するのが基本です。Joget プロジェクトの標準構成：

```
my-joget-project/
├── pom.xml                               ← Maven 座標
├── src/main/java/...                     ← プラグイン／ユーティリティのソース
├── src/main/resources/properties/*.json  ← コンポーネント設定項目の定義
├── src/main/resources/messages/*.properties
└── APP_XXX-1-2024....jwa                 ← プロジェクト同梱のサンプルアプリ
```

ディレクトリ内を自動判別し、`.jwa` をアプリとして、Maven プロジェクトをプラグインソースとして解析したうえで、**両者を突合**します。

「ファイルをアップロード」から `.jwa` 単体（任意でプラグインソースの zip を添付）を解析することもできます。

## 生成物

| 生成物 | 内容 |
|---|---|
| `app_summary.json` | フォーム / データリスト / メニュー / XPDL プロセス / テーブルモデル / SQL 副作用 / 影響マトリクス |
| `plugin_manifest.json` | プラグインコンポーネント、設定項目定義、クラス呼び出し関係 |
| `correlation.json` | **アプリ設定 ↔ プラグインソースの三者突合** |
| `design_doc.md` | 全 7 章の設計書（2.3 突合章を含む） |
| `rag_chunks.jsonl` | 18 種類のチャンク。そのままベクトル化して投入可能 |

## セットアップ

```bash
npm install
npm start          # http://localhost:3000
```

開発モード（フロントのホットリロード）：

```bash
npm run dev        # Vite dev server（/api は 3000 にプロキシ）
npm start          # 別ターミナルでバックエンドを起動
```

### 画面が守る約束

- **確定と推測を混ぜない。** 各オブジェクトに解析状態（解析済 / 一部のみ / 未確認 / 解析失敗）を付け、根拠を必ず示せます。
- **未確認を 0 や空欄にしない。** 未検出は「未計測」と表示し、解析の到達範囲をそのまま伝えます。静的チェックでも「調べたが何も出なかった」（0 件）と「調べられなかった」（未計測）を区別します。ルールの名前・検査範囲・解析上の制限は統合オブジェクトモデルのカタログ（`CHECK_RULES`）が持ち、画面は同じ定義元を引きます。
- **未確認には必ず成因を付ける。** 「どこまで読めたか」（状態）と「なぜ読めなかったか」（成因）は別の軸です。ソースが無いだけのものとアプリ定義自体が欠けているものを分けて示せます。成因の語彙と判定は統合オブジェクトモデル側にあり、画面は同じ定義元を引きます。
- **読めた範囲を、読めた以上の広さで言わない。** SQL は「列まで読めたもの」と「参照先テーブルまで読めたもの」が混在します。列まで読めているのはプロセス内のデータベース更新ツールが実行する UPDATE 文だけで、データリストのクエリやフォームの選択肢取得 SQL の列は検査していません。到達範囲はモデル（`sqlCoverage`）が持ち、静的チェックの検査範囲・品質画面の注記・データモデルの SQL タブが同じ定義元を引きます。
- **テーブルは命名規約からの導出。** 実データベースのメタデータは参照しません。
- **列の出処を 1 行 1 列で明示。** 各カラムに「フォーム定義 / 実データ / 監査列 / 根拠不明」のバッジを付け、導出なのか実在確認なのかを色と文字の両方で示します（語彙と凡例はモデル側が持ち、画面は同じ定義元を引きます）。
- **実行時の挙動は断定しない。** クエリ・変数・プラグインの動的挙動は静的解析の範囲外として明示します。
- **一覧の件数と行数を一致させる。** 見出しの件数は画面が数えた件数、行は実際に描かれた行です。両者が食い違うのは、同じ対象が二重に出ているか、前の描画が残っているときで、どちらも一覧から対象を開けない不具合になります。件数と行数は別々の経路から取るので、片方が壊れてももう片方は正しいままです。
## 設計上の要点

**1. テーブルモデルはフォーム定義を基準にします。** `.jwa` 内の `data/*.json` は、エクスポート時に「データを含める」を選んだ場合にのみ存在します。そのため物理テーブルはフォーム定義から導出します：`tableName` → `app_fd_<tableName>`、フィールド → `c_<fieldId>`（レイアウト要素は除外）。さらに `id / dateCreated / dateModified / createdBy / modifiedBy` の監査列を補います。サンプルデータはサンプル値と件数の補完にのみ使用するため、データをエクスポートしていなくても ER 図が空になることはありません。

**2. 解析範囲を単一プロジェクトに厳密に限定します。**

- ツール自身のディレクトリは決して走査対象にしません。
- `.jwa` は「同一ディレクトリまたは上位ディレクトリ」の Maven ルートとのみ対応付け、下位ディレクトリとは対応付けません。
- ディレクトリ内に独立したプロジェクトが複数ある場合は自動選択せず、明示的な指定を求めます。

目的は**別プロジェクトのファイルを混在させないこと**です。

**3. 「何が存在するか」の推导は 1 箇所にまとめます。** 画面（オブジェクト一覧・プラグイン画面）と設計書生成は、統合オブジェクトモデル（`lib/objectModel.js`）が組み立てるオブジェクトを読みます。設計書の 2.1（機能モジュール）・2.2（コンポーネント・プラグイン一覧）・3.x（フォーム設計）・5.1（テーブル構造一覧）・6.x（影響範囲）はこのモデルから生成し、生成側が `app_summary.json` を独自に歩かないようにしています。同じ結論が二箇所に並ぶと、片方だけが壊れても気づかないためです。プラグインの集合は「アプリ定義が参照するクラス」（`plugin_refs`）を基準にし、プラグインソースとの突合結果はその後で重ねます——ソースが無いプロジェクトでも、参照されていることは `.jwa` だけで確定しています。

影響範囲（どのフォーム・SQL・リストがどのテーブルを読み書きするか）もモデルが組み立てます（`model.impact`）。モデルは物理テーブル名（`app_fd_xxx`）で語るので、設計書 6.x のテーブル名は 5.1 と同じになり、章をまたいで同じテーブルを追えます。一方 `app_summary.json` の `impact` は `data/*.json` の名前空間（接頭辞なし）で契約されているため、解析エンジンがキーを変換してから書き出します——画面・RAG・Mermaid は従来通りの形で読み続けられます。

静的チェックのルールの語彙（ルール名・検査範囲・解析上の制限）もモデルのカタログ（`CHECK_RULES`）が持ち、`buildChecks` はカタログを引いて各結果に書き出します。画面のルールサマリ（`model.checkRules`）はこのカタログに件数と計測可否を添えたものなので、結果が 0 件でも「調べた」事実が消えず、ソース未提供で計測できないルールは 0 件ではなく「未計測」として区別されます。

**4. オブジェクトの同一性は「親 + 子の ID」で決めます。** 項目ID はフォームの中で一意とは限らず、アプリ全体でも一意ではありません。Joget のセクション項目は `section1` / `section2` という機械的な ID を複数のフォームで使い回し、同じフォームの中に同じ ID が 2 回現れることもあります（`fixtures/jwt-sso-webservice` の `public_key`）。ID だけを鍵にすると別の対象が 1 つに潰れ、`byKey` から引けないオブジェクトができます——しかも一覧の件数は総件数のままなので、数字を見ても気づけません。そこで、カラムは「テーブル名.カラム名」、プロセスのノードは「プロセスID.ノードID」、フォーム項目は「フォームID.項目ID」を鍵にし、**同一フォーム内の重複は 1 つにまとめたうえで、まとめた事実を静的チェックの注記として残します**（黙って重複を捨てない）。`test-object-model.mjs` が「key が一意」「`byKey` から全件引ける」を毎回確かめます。

## 動作確認

`fixtures/` に解析用のサンプルを同梱しています（詳細は `fixtures/README.md`）。

```bash
npm start          # 別ターミナルで起動しておく（画面テストはブラウザを使う）
npm run test:all   # まとめて実行（推奨）
```

`test:all` は `fixtures/` にある解析対象をすべて自動検出し、
対象ごとに同じ検査を流します。実行できなかった対象は
「スキップ」として必ず一覧に出ます（門が黙って緑にはなりません）。

| 検査 | 内容 |
|---|---|
| 単一言語チェック | 簡体字・中国語句読点・無関係言語の残留（0 件で合格） |
| 解析エンジン | フォーム・プロセス・SQL の抽出 |
| プラグイン突合 | アプリ設定とプラグインソースの突合 |
| 図の生成 | Mermaid が実際にパースできるか（空プレースホルダも検出） |
| プラグインソース走査 | properties 宣言と Java 読み取りの走査 |
| 統合オブジェクトモデル | 関連の解決・双方向性・未確認の明示・キーの妥当性・設計書の各節との突合 |
| 画面テスト | 全画面・図の描画・日本語表示・ページエラー |
| 開発サーバー変換テスト | Vite dev で CJS が ESM に変換され、画面が実際に動くか |

個別に実行することもできます。

```bash
npm run verify:lang          # 日本語のみになっているかのゲート
npm run test:ui              # 画面テスト（既定は同梱サンプル）
npm run test:object-model    # 統合オブジェクトモデル
```

### 解析対象を切り替える

`fixtures/` に同梱されるのは Apache-2.0 のサンプルだけなので、
そのままでは「小さいアプリ」に対する検証しかできません。
実際のお客様の `.jwa` を置いておくと、
早めに検出できたはずの不具合が CI に出ないまま成品になります。

```bash
# 顧客アプリを fixtures/ に置く（.gitignore 済みなので commit されない）
mkdir -p fixtures/my-app && cp /path/to/APP_XXX.jwa fixtures/my-app/

# 個別に実行
JOGET_PROJECT="$PWD/fixtures/my-app" npm run test:ui
JOGET_PROJECT="$PWD/fixtures/my-app" npm run test:object-model

# test:all は_FOUND_した対象を自動で回す
npm run test:all
```

`JOGET_PROJECT` には `.jwa` ファイルを指定しても、
そのディレクトリを指定しても構いません。

### 「緑だが何も検査していない」状態を作らない

このリポジトリでは門そのものに関する失敗が 5 度ありました。
いずれも「テストは通っているのに、壊れたまま納品される」形です。

| 症状 | 原因 | 対策 |
|---|---|---|
| Mermaid の空図が検出されない | SVG 要素に `innerText` は常に空文字を返す | `textContent` を使う |
| 関連が 0 本でもテストが通る | 解決に失敗した関連は `links` に入らず `unresolved` に落ちるだけ | `unresolved` も必ず検査する |
| 画面テストが常に緑 | 想定した解析対象でしかアサーションが成立しない | 全解析対象を自動検出して回す |
| build は通るが dev が真っ白 | Vite の本番ビルドと開発サーバーは CJS 変換の経路が別 | `test-dev-transform.mjs` で dev も門に含める |
| アンカーが 1 件でも紐づけば通る | 「どこかの章に紐づけばよい」では章の間違いを拾えない | 自分の節が入っている章に紐づくことを検査 |
| 語彙を二重に持つ | 生成側と参照側が同じ見出し文字列を直書き | 章語彙を `lib/objectModel.js` の 1 箇所に集約する |

新しい検査を追加するときは、**意図的に不具合を戻して検出できることを必ず確認**してください。
検証していない検査は、止まったままの検査と同じです。

## 技術スタック

解析は純粋な Node.js（Express + adm-zip + fast-xml-parser）、フロントは React 18 + Vite + Tailwind CSS v4、図は Mermaid をフロント側で描画。**データベースは使用しません** —— 結果は `data/runs/<id>/out/` に出力されます。
