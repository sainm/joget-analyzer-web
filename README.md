# joget-analyzer-web

Joget DX 应用包（`.jwa`）与插件源码的**逆向分析工具**。指向一个工程目录，自动产出设计书、影响分析、调用关系图与 RAG 分块。

界面支持**中文 / 日本語**双语，默认跟随浏览器语言。

> 事实靠解析 · 语义交 AI —— 所有结构性结论都来自本地解析，不调用任何外部服务，也不需要数据库。

---

## 中文

### 输入方式

首选**指向本机工程目录**。一个 Joget 工程通常长这样：

```
my-joget-project/
├── pom.xml                               ← Maven 坐标
├── src/main/java/...                     ← 插件与工具类源码
├── src/main/resources/properties/*.json  ← 组件配置项定义
├── src/main/resources/messages/*.properties
└── APP_XXX-1-2024....jwa                 ← 随工程附带的样例应用包
```

工具会自己识别目录里有什么：`.jwa` 当应用分析，Maven 工程当插件源码分析，然后**把两者对起来**。

也可以退回到「上传文件」入口，单独上传 `.jwa`（可选附带插件源码 zip）。

### 产出物

| 产物 | 内容 |
|---|---|
| `app_summary.json` | 表单 / 数据列表 / 菜单 / XPDL 流程 / 表模型 / SQL 副作用 / 影响矩阵 |
| `plugin_manifest.json` | 插件组件、配置项定义、类级调用关系图 |
| `correlation.json` | **应用配置 ↔ 插件源码三方比对** |
| `design_doc_zh.md` / `design_doc_ja.md` | 7 章设计书（含 2.3 联动章） |
| `rag_chunks.jsonl` | 18 种类型的分块，可直接入库做向量化 |

### 快速开始

```bash
npm install
npm start          # http://localhost:3000
```

开发模式（前端热更新）：

```bash
npm run dev        # Vite dev server，/api 代理到 3000
npm start          # 另开一个终端跑后端
```

### 两个设计要点

**1. 表模型以表单定义为基准。** `.jwa` 里的 `data/*.json` 只有在导出时勾选「包含数据」才存在。因此物理表由表单定义推导：`tableName` → `app_fd_<tableName>`，字段 → `c_<fieldId>`（过滤布局控件），再补 `id / dateCreated / dateModified / createdBy / modifiedBy` 五个审计列。样例数据只用于补充示例值与记录数 —— 没导出数据也不会让 ER 图变空。

**2. 分析范围严格收窄到单一工程。**

- 工具自身目录永不参与扫描；
- `.jwa` 只与「同目录或上层目录」的 Maven 根配对，不与下级目录配对；
- 目录下存在多个独立工程时拒绝擅自选择，要求明确指定。

目的是**不把不同工程的文件混在一起**。

### 技术栈

纯 Node.js 解析（Express + adm-zip + fast-xml-parser），前端 React 18 + Vite + Tailwind CSS v4，图表用 Mermaid 在前端渲染。**不使用数据库** —— 结果落在 `data/runs/<id>/out/`。

## 日本語

Joget DX のアプリケーションパッケージ（`.jwa`）とプラグインソースを**リバース解析**するツールです。プロジェクトディレクトリを指定すると、設計書・影響分析・呼び出し関係図・RAG チャンクを自動生成します。

UI は**中文 / 日本語**のバイリンガル。ブラウザの言語設定に自動追従します。

> 事実は解析で · 意味づけは AI で —— 構造的な結論はすべてローカル解析によるもので、外部サービスもデータベースも使いません。

### 入力方法

**ローカルプロジェクトのディレクトリを指定**するのが基本です。Joget プロジェクトの標準構成：

```
my-joget-project/
├── pom.xml                               ← Maven 座標
├── src/main/java/...                     ← プラグイン／ユーティリティのソース
├── src/main/resources/properties/*.json  ← コンポーネント設定項目の定義
├── src/main/resources/messages/*.properties
└── APP_XXX-1-2024....jwa                 ← プロジェクト同梱のサンプルアプリ
```

ディレクトリ内を自動判別し、`.jwa` をアプリとして、Maven プロジェクトをプラグインソースとして解析したうえで、**両者を突合**します。

「ファイルをアップロード」から `.jwa` 単体（任意でプラグインソースの zip を添付）を解析することもできます。

### 設計上の要点

**1. テーブルモデルはフォーム定義を基準にします。** `.jwa` 内の `data/*.json` は、エクスポート時に「データを含める」を選んだ場合にのみ存在します。そのため物理テーブルはフォーム定義から導出します：`tableName` → `app_fd_<tableName>`、フィールド → `c_<fieldId>`（レイアウト要素は除外）。さらに `id / dateCreated / dateModified / createdBy / modifiedBy` の監査列を補います。サンプルデータはサンプル値と件数の補完にのみ使用するため、データをエクスポートしていなくても ER 図が空になることはありません。

**2. 解析範囲を単一プロジェクトに厳密に限定します。**

- ツール自身のディレクトリは決して走査対象にしません；
- `.jwa` は「同一ディレクトリまたは上位ディレクトリ」の Maven ルートとのみ対応付け、下位ディレクトリとは対応付けません；
- ディレクトリ内に独立したプロジェクトが複数ある場合は自動選択せず、明示的な指定を求めます。

目的は**別プロジェクトのファイルを混在させないこと**です。

### 技術スタック

解析は純粋な Node.js（Express + adm-zip + fast-xml-parser）、フロントは React 18 + Vite + Tailwind CSS v4、図は Mermaid をフロント側で描画。**データベースは使用しません** —— 結果は `data/runs/<id>/out/` に出力されます。
